# Field Report

Discord bot that posts weekly or monthly cEDH meta reports, filtered to a region each server configures. The only data source is the TopDeck.gg API v2.

## Current milestone

Milestone 8: post redesign (one message with four embeds, a headline, medals, line icons, share bars and color identity squares; see Post layout below). Milestone 7 (custom regions: a server admin builds a region from cities, states, countries, continents, seeded regions and a radius around a city, several places per command; see Custom regions below), milestone 6 (player data and player sections, permitted by TopDeck, `docs/permissions.md`) and milestones 1–5 (ingestion, classification and geocoding, region catalog and stats, post composer, the Discord app on Vercel) are done. The bot is still gated to one private test server: do not open the bot to other servers (ALLOW_ALL_GUILDS, global command registration) until the user approves.

## Pipeline

- `npm run migrate`, then `npm run refresh` (backfill the last 2 full months, then classify, standings, geocode, regions, pair-commanders and color-identity; stops on the first failure). Use `npm run backfill -- --months N` for longer history; player history uses 36 months.
- Players: backfill stores each standings row's TopDeck player id in `entries.player_id` and upserts `players (player_id, display_name)`, refreshing the name on every ingest (the window's latest event wins). "Deleted User" or a missing name is stored as a null name. Windows logged before player ids existed (`ingest_log.has_players = false`) are fetched again, so `backfill --months 36` is resumable without `--force`.
- Opt-outs: `npm run optout -- add <player_id> [--note "..."] | remove <player_id> | list` manages `player_optouts`. Adding blanks the stored name, and ingest keeps it blank while the opt-out exists. Every output reads names through the `player_names` view, which returns a null name for opted-out players. Never read `players.display_name` directly in a stat, script or post.
- Partner validation: `npm run pair-commanders` (scripts/fetch-pair-commanders.ts, in `refresh` just before `color-identity`) replaces `pair_commanders` with Scryfall's `oracletag:pair-commander` list, one row per name a pair half can be written as (Oracle name, each face of a "Front // Back" card, and printed or flavor names of individual printings). It skips the fetch when the list is under 24 hours old (`--force` overrides) and writes nothing if the response is incomplete or under 50 cards. `qualifying_entries.is_valid_pair` is null for a non-pair leader or an unfilled list, true when the leader is exactly two names that are both in the list, false otherwise. Names are compared on `card_name_key` (lower case, straight apostrophes; the same rule as `cardNameKey` in `scripts/lib/scryfall.ts`). Commander stats exclude invalid pairs through `qualifying_entries.leader` (next bullet). `npm run pair-report` prints the impact and name-matching report; it is read-only and fetches the lists into memory, so it also runs before the table exists.
- Color identity: `npm run color-identity` (scripts/fetch-color-identity.ts, last step of `refresh`) replaces `commander_colors` (migration 017) with the color identity of every card that can be a commander: one Scryfall search, `is:commander or oracletag:pair-commander` (the tag adds the Backgrounds), one row per card, 23 pages at 1 request per second. It stores one row per name a commander can be written as (the Oracle name and each face of a "Front // Back" card) with `colors`, a subset of `WUBRG` in that order ('' for colorless). It skips the fetch when the list is under 24 hours old (`--force` overrides) and writes nothing if the response is incomplete or under 1,000 cards. `commander_color_identity(leader)` gives a registered leader's colors: each half of a pair is looked up on `card_name_key`, a half that is not a card name is tried as a printed name through `pair_commanders.card_name` ("Will the Wise" is Wernog, Rider's Chaplain), a pair is the union of its halves, and the result is null when any half has no match. This is decoration only: no stat reads it, and an empty table only means the post shows no color squares. `loadPostData` reads it once per post, for the commanders a section can show (`commandersShown`), into `PostData.colors`. `npm run color-report` prints the match report; it is read-only and fetches the list into memory, so it also runs before the table exists.
  - Observed November 2026 (`color-report`, Supabase, May–October 2026, qualifying entries with a commander): Scryfall returned 3,912 cards, stored as 4,212 names (79 colorless, 1,892 one color, 1,383 two, 467 three, 18 four, 73 five). 1,038 of 1,044 distinct registered commanders match (99.43%), which is 41,171 of 41,179 entries (99.98%). 1,036 match on Oracle names exactly; the apostrophe key adds none in this window (the typographic apostrophes are all from 2025); 2 more match through a printed name in `pair_commanders` (Eleven, the Mage / Mike, the Dungeon Master, and Lucas, the Sharpshooter / Will the Wise, 1 entry each).
  - Not matched in the same run, so shown without squares: 6 commanders with 8 entries. Kavaero, Mind-Bitten (3 entries), Blanka, Ferocious Friend and Egrix the Bile Bulwark (1 each) are not among the 4,212 stored names; whether a fetch of one row per printing would find them was not checked (it would take about three times the pages). Izzet Guildmage, Seedglaive Mentor and Demonic Tutor / Killian, Ink Duelist (1 each) name cards that are not in Scryfall's commander list.
  - Cost, observed November 2026 on a local copy of the Supabase data: the lookup takes about 65 ms for the global post's 104 commanders and 30 ms for Pacific Northwest's 54, against 2–6 s for the rest of `loadPostData`.
- `classify` recomputes `event_class`, `series_key` and `leader_coverage` for all tournaments and must run after every backfill: new events change series averages. `series_overrides` wins over the computed class.
- `geocode` derives country, admin-1 and admin-1 group from lat/lng only; location strings are never used for regions. It needs the boundary file in `data/` (see Hard rules). Backfill clears the geo fields when a tournament's lat/lng change.
- Radius centers: `npm run places` (scripts/load-populated-places.ts) loads Natural Earth's populated places from the pinned file in `data/` into `populated_places` (see Hard rules), so a city with no events of its own (Seattle) can be the center of a radius place. Run it once after migration 016; it is not part of `refresh`, because the file is pinned and never changes. It verifies the file's SHA-256, geocodes every point with the admin-1 boundary file (both files must be in `data/`), so country and admin-1 codes are the ones events carry (Natural Earth's own `iso_a2` is not used), and replaces the table in one transaction: upsert, then delete rows no longer in the file. It writes nothing when the file has fewer than 1,000 places. Observed November 2026: 7,342 places stored, geocoded 7,324 exact, 13 nearby and 5 without a country (kept with null codes and never offered as centers). The bot and the Vercel app read the table and never the file.
- Stats read from the `qualifying_entries` view (16+ players, `event_class` in cedh or unlabeled_competitive). Its `leader` column is the commander used for stats, not the raw registered text (migration 013): typographic apostrophes are made straight (`normalize_leader`), and it is null when the leader is an invalid partner pair, so every stat that groups or filters on `leader` drops those entries the same way it drops entries with no commander. `registered_leader` is what was registered (apostrophes normalized, never nulled); use it where the registered deck should still show: Top players' most-played commander and the "entries with decklists" coverage figure. Winners and event results read `entries` directly and show the raw registered text. Group commanders on `qualifying_entries.leader`, never on `entries.leader`, or apostrophe variants split again. Cost, observed November 2026 with SELECTs emulating the view on Supabase: grouping the global 6-month window by commander goes from about 0.06 s to 0.18 s of server time.
- `regions` adds every country, admin-1 group and admin-1 unit with a qualifying event in the last 12 months (ids like `us`, `es-cataluna`, `us-wa`). It never deletes regions or changes seeded ones. Fallback parents: admin-1 -> group -> country -> macro -> global.
- In SQL, filter a region with `tid in (select r.tid from region_tournament_ids(p_region) as r(tid))` (the function in FROM, so the planner can inline it), and compute event results for a few events with `tournament_results_for(tids)` rather than the whole `tournament_results` view. Observed November 2026 after the 36-month backfill: with the function in a select list, global `stat_conversion` ran past Supabase's 2-minute statement timeout; migration 010 brought every stat the post uses under 2 s. `stat_notable_results` (used only by `report`) still takes about 14 s for global.
- Stats are SQL functions taking `(region_id, end_month)`: `region_reportability`, `resolve_region`, `stat_meta_share`, `stat_ppg`, `stat_conversion`, `stat_growth`, `stat_notable_results`, `stat_coverage`, plus the player stats `stat_top_players` and `stat_rising_players` (see Player stats below). `npm run report -- --region <id> --month YYYY-MM` prints them for review.
- `scripts/lib/post.ts` composes the monthly post (v3 newsletter): `loadPostData` reads the stat functions, `composePost` (pure) returns the embeds of one Discord message and a text preview. Sections: scene this month, winners (up to 10 largest qualifying 32+ events, with the winner's name), top players, rising players, top-cut appearances, most played (6-month snapshot, no movement markers; Rising commanders and Cooling commanders show movement), best results, top-cut conversion, rising commanders, cooling commanders, coverage, Sources. The two player sections need no decklists, so they also show for non-reportable regions. In Winners an opted-out winner is "a player" and a winner with no known name shows the commander alone; opted-out and removed players never appear in the player sections. Thresholds and caps are in `POST_CONFIG`; posts stay under a 5,300-character content budget (`contentBudget`, counted across all embeds) and Discord's limits (10 embeds and 6,000 characters per message across all its embeds; per embed 256 for the title, 4,096 for the description, 25 fields and 1,024 per field value), and organizer text and player names are sanitized. Lengths are JavaScript string lengths, which count an emoji as 2 or 3, so they are never below Discord's count. Trim order when over budget: the top-cut lines lose detail (both shares, then the ratio, then the count alone); then decoration goes before any data (blank spacing, share bars, color squares); then the decks block trims bottom-up (each section to a floor, then deeper); then Top players and Rising players; Winners last (to 5, then 3). The headline, the scene, Coverage and Sources never trim. Observed on the October 2026 fixtures: global 4,734 characters in 4 embeds (3,834 in one embed before the redesign), Europe 4,746 (3,822), Pacific Northwest 3,999 (3,209), the Seattle Metro custom region 2,920 (2,217); nothing is trimmed, and the longest field is 633 characters (Pacific Northwest's Winners). The Rising players field name states its window ("first win or top cut in 3 years of data", `POST_CONFIG.playerHistoryYears`; change it if the backfill depth changes). The coverage line also shows the share of the month's qualifying entries with an account id (`stat_player_coverage`), e.g. "96% of October entries have a linked player". Region labels come from `region_label` and never show the region type. `npm run preview -- --region <id> --month YYYY-MM` prints a post; `npm test` runs the composer tests on fixtures in `test/fixtures` (no database).
- Post layout: one message with up to four embeds, each with a short title and its own accent color (`POST_CONFIG.embeds`). An embed with no sections is left out, and there are no divider fields. `/preview` and the cron send all embeds in one message.
  - Embeds, in order: the month in numbers (title "<region> — cEDH meta, <Month> <Year>", gold; its description holds the fallback notes and then the headline; the scene is one row of three inline fields, Discord's maximum per row, with Largest event at full width under it); people ("👥 Players — October", blue: Winners, Top players, Rising players); decks ("🃏 Commanders — October", green: Top-cut appearances, Most played, Best results, Top-cut conversion, Rising commanders, Cooling commanders); and "ℹ️ About this report" (grey: Coverage, then Sources with the linked TopDeck attribution, always the last field of the last embed). The people sections' names don't repeat the month, because the embed title carries it; Top-cut appearances keeps it, because the decks embed mixes the month with 6-month sections. Each section's field name starts with an emoji (the scene's goes on its first field).
  - Headline (`headline`, `headlineCopy`, `headlineMinCuts`): up to three lines, each left out when its data is missing. It is computed from the untrimmed lists and never trimmed. Line 1 is the first Winners row with its winner ("… went to **Mara Ellison** on Kraum / Tymna the Weaver"), "was the biggest event" when that event has no single winner, or the scene's largest event when the region has no 32+ event. Line 2 is the month's top-cut leader when one commander has strictly the most top cuts and at least 5; otherwise the most played commander with its 6-month share, naming the borrowed region in a mixed-scope post ("… in Washington"). Reason for that order: the top-cut leader changes month to month and the 6-month leader rarely does. Line 3 is the first Rising commanders line, else the first Rising players line. Observed on the October 2026 fixtures: global and Pacific Northwest show the top-cut leader; Europe has a tie at 35 cuts and shows the most played commander.
  - Lines: an item gets a second line when its detail is a phrase (Winners: the event and its size, then "🏆 player on commander"; Top players; Rising players; Top-cut appearances; Rising and Cooling commanders) and stays on one line when its detail is one number (Most played, Best results, Top-cut conversion). Ranked lines start with 🥇🥈🥉, then 4️⃣ to 🔟 (`medals`, `rankSymbols`); past the tenth, or with medals off, they are written `1\.` so Discord doesn't restyle them as a markdown list (the text preview shows `1.`). Line icons (`lineIcons`): 🏆 wins, 🎯 top cuts, 🆕 a new commander, 🔥 a riser, 🧊 a cooling one. Event names in Winners, player names and the deck sections' commander names are bold (`boldNames`). Winners have a blank line between them (`spacing`, a switch per section).
  - Winners past 1,024 characters become two fields: the first `winnersSplitAt` (5), then the rest under a zero-width name (`continuedFieldName`), so every winner still shows; lines are dropped only if a half still doesn't fit. Observed on the October 2026 fixtures: the global and Europe posts split (ten winners each); Pacific Northwest (six) does not.
  - Share bars in Most played (`shareBars`, `barWidth` 10, `barFilled` ▰, `barEmpty` ▱) are scaled to the top commander's share, with at least one cell filled. The glyphs take the text color, so they read on both themes; blue squares would read as blue mana next to the color squares.
  - Color identity squares follow a commander's name (`colorSquares`, `colorSymbols`), in WUBRG order, from `PostData.colors`: 🟨🟦🟪🟥🟩, 🔘 for colorless, nothing for a commander with no match. Yellow stands for white and purple for black, because Discord draws ⬜ (#E6E7E8) and ⬛ (#31373D) in almost the color of its light and dark embed backgrounds, so each would disappear on one theme. The headline shows no squares.
  - Every look option is a `POST_CONFIG` switch (`headline`, `medals`, `lineIcons`, `boldNames`, `winnersTwoLines`, `detailOnSecondLine`, `spacing`, `shareBars`, `colorSquares`, `largestEventInline`, `sectionEmoji`, `embeds`). With all of them off, each section's lines are character for character the ones from before the redesign (checked against the old snapshots of all four fixtures when the redesign was made). Cost on the global October 2026 fixture, each switch turned off alone: color squares 286 characters, headline 277, bold names 199, share bars 110, winners on two lines 99 (and 10 lines), line icons 83, blank lines between winners 8 (and 8 lines); putting details on a second line costs no characters but 18 lines, and medals cost none. Everything off is 3,768 characters and 82 preview lines, against 4,734 and 122. How it looks in Discord is not verified by tests; check with `/preview` (both themes, desktop and phone) after changing these.
- Post details (migration 014):
  - Rising commanders calls a commander new in two ways. "new since Sep 26": its first qualifying entry anywhere in our data (`stat_share_trend.first_seen`, worldwide and not per region, UTC date) is in the report month or the month before (`POST_CONFIG.newCommanderMonths`, 2), even if it already has entries in the prior 3 months. Plain "new": no entries in the region in the prior 3 months but an older first entry. Both kinds list before the share-growth risers, most entries first, and neither can appear in Cooling commanders. Reason: Dack Fayden, Helping Hand first appeared on 2026-09-26 (4 entries) and so read "93 entries in October (avg 1/month)".
  - Top-cut appearances shows each commander's share of the month's top cuts against its share of the field: "157 cuts · 9.2% of cuts vs 8.5% of field". Field means entries with a commander in the month's events that had a top cut (an event where any entry played bracket games), in the region; entries in events with no recorded cut are left out, or a commander popular there would look as if it underperformed. Under budget pressure the line shortens to "157 cuts · 1.08× its field share", then "157 cuts" (`POST_CONFIG.topCutDetail`), before any line is trimmed.
  - Cost of `first_seen`, observed November 2026 on Supabase: one pass over all qualifying entries per post, about 0.36 s of server time reading `entries` directly (about 1.0 s through `qualifying_entries`, which is why it doesn't use the view).
- Custom regions (migration 015, `src/server/custom-regions.ts`): see the Custom regions section below. In short: a guild-owned region is a row in `regions` with `owner_guild_id` set and its places in `region_places`; every stat takes its id like any other region; when it is not reportable its post mixes scopes (`PostData.statsRegion`). Migration 016 adds radius places ("within 50 km of Seattle") and adding or removing several places in one command.
- `standings` (scripts/fetch-standings.ts) fills `event_winners` with the official standing-1 commander and player id for qualifying 32+ events with topCut = 0, once per event, 1 request per second, and upserts that player into `players`. Rows fetched before player ids were stored (`player_checked_at` is null) are fetched once more.
- Discord app: `guild_configs` holds each server's region (default global), channel and last posted month. `regions.selectable` controls what `/region set` offers (every country; groups in ES, IT, GB, FR, PT; admin-1 in US, CA, DE, AU). Commands: `/region set|show|create|add|remove|delete|list`, `/channel set`, `/preview`, admin-only (Manage Server), deferred when they touch the DB. Autocomplete (3-second limit) serves standard regions, places and radius centers from per-instance caches (10 minutes) and reads a server's own regions fresh each time. The cron posts the previous month's report on or after the 15th, only when `ingest_log` has that month, claims each guild atomically (at most one post per month), sends the post as one message holding all its embeds, sends every message with `allowed_mentions: { parse: [] }`, and prunes configs and custom regions for guilds the bot has left (there is no HTTP event for removal; the prune runs only once the cron is past its post-day and data gates, so it can lag by weeks).
- Guild gate: `ALLOWED_GUILD_IDS` (comma-separated) fails closed; only `ALLOW_ALL_GUILDS=true` opens the bot to every server. Register commands with `npm run register-commands -- --guild <id>` (again after any change to `src/server/commands.ts`); `--global` needs `--confirm-global`. Setup steps: `docs/deploy.md`.
- Tests: `npm test`. The Postgres-backed tests (`test/discord-db.test.ts`, `test/players-db.test.ts`, `test/pair-commanders-db.test.ts`, `test/custom-regions-db.test.ts`, `test/bulk-radius-db.test.ts`, `test/commander-colors-db.test.ts`, part of `test/standings.test.ts`) run only when `TEST_DATABASE_URL` is set. They share one database and run in parallel, so each file uses its own id prefix and its own months (players 2031-03, pairs 2032-04, custom regions 2034-03, bulk and radius 2036-06). The two custom-region files also insert standard regions when the database lacks them and remove them afterwards, so they use different ones (United States, Canada and Spain in one; Germany and Austria in the other), and each file's fake Discord client lists the other files' servers as still joined, or its cron prune would delete their regions. `test/bulk-radius-db.test.ts` shadows `populated_places` with a temporary table for its own connection, so it does not depend on the real file being loaded and can replace the table; stats that look worldwide (`first_seen`, player history) can see another file's rows, so assert only on names unique to the file. `test/discord-db.test.ts` is the only one that needs ingested data (it expects September 2026 in `ingest_log` and real regions); the others create their own rows. `test/commander-colors-db.test.ts` shadows `commander_colors` and `pair_commanders` with temporary tables for its own connection, because the pair test rewrites `pair_commanders` while it runs.

## Custom regions

A server admin builds a region out of places and uses it as the server's region: `/region create`, `/region add`, `/region remove`, `/region delete`, `/region list`; `/region set` offers the server's own regions first; `/region show` lists the places and where commander stats come from. `/region add` and `/region remove` take several places in one command, and a place can be a radius around a city (migration 016).

- **Schema (migration 015).** A custom region is a row in `regions` with `owner_guild_id` set (`type = 'custom'`, `source = 'guild'`, not selectable, no parent, id `g:<guild id>:<8 hex>`, which can't collide with a standard slug). Its places are rows in `region_places`, one per place the admin added: a member region (any selectable standard region except Global, resolved through that region's `region_members` when stats run, so Europe stays one place), a city (`country_code`, `admin1_code`, `city_key`), or a whole country by code for a country with no region row yet. Standard regions (`owner_guild_id` null), their ids and their results are unchanged: all 108 stat checks on a local copy of the Supabase data hash identically before and after. Migration 016 adds a fourth kind of place, a radius: `center_lat`, `center_lng`, `radius_km`, the center's `country_code` and `admin1_code`, the label ("within 50 km of Seattle, Washington, United States") and a stored bounding box (`min_lat` … `max_lng`, generated columns). The check constraint `region_places_shape` allows exactly the four shapes; its radius branch tests `is not null` explicitly, because a check that evaluates to null passes.
- **Why the same table:** every stat function, `region_label`, the cron's per-region cache and the `guild_configs.region_id` foreign key take a region id, so a custom region works everywhere without a second code path. `resolve_region`, `region_reportability` and `guild_configs` did not change.
- **Ownership.** Every query for custom regions filters on the calling server's id (`src/server/custom-regions.ts`). Triggers back this up in the database: `guild_configs` rejects a region owned by another server, and `region_places` rejects a member that is not a standard region. Names are unique per server (case-insensitive), not globally, and can't equal a standard region's name or id. Any new query that lists regions for users must add `owner_guild_id is null` or filter by the server.
- **Cities.** Matched on `city_key(city)` (trimmed, lower case, whitespace collapsed) within the event's geocoded country and admin-1, so Vancouver, British Columbia and Vancouver, Washington are different places. Autocomplete lists only cities with a qualifying event in the last 12 months (`region_city_options`), labelled "Tacoma, Washington, United States (35 events)"; a typed name has to match one of them (see Bulk add and remove below). Index: `tournaments_city_idx`.
  - Observed November 2026 (Supabase, qualifying events, November 2025 – October 2026): 3,602 events, 2,971 (82%) with a city; every event with a city is geocoded with an admin-1; 172 geocoded events have no city (only a state or country place reaches them) and 459 have no location. 650 distinct (country, admin-1, city) triples in 12 months, 819 all time.
  - Observed in the same data: normalization collapses nothing (0 of 819 triples have more than one raw spelling), and about 10 near-duplicate pairs stay separate ("makati" / "makati city", "dillingen" / "dillingen/saar"). An admin can add each.
  - **A city is the venue's municipality, not the metro.** Observed in the same data: Washington has events in Tacoma (57 all time), Spokane Valley 16, Spokane 16, Issaquah 11, Lacey 11, Pullman 4, Bremerton 4, and none in Seattle, Bellevue, Everett, Renton, Kent, Kirkland, Redmond or Olympia. A metro has to be built from the cities the list offers.
  - Observed November 2026: 146 countries that a continent lists have no region row because they have no qualifying event (Luxembourg among them), which is why a country can be a place by code alone.
- **Radius places (migration 016).** "Within N km of a center" is one place. An event belongs when its stored coordinates are within N km of the center (`haversine_km`, plain SQL, mean Earth radius 6,371.0088 km; no PostGIS or earthdistance). An event without coordinates can never match. Overlap with other places counts once, as for every place.
  - Range and default are in `REGION_CONFIG`: `radiusMinKm` 10, `radiusMaxKm` 200, `radiusDefaultKm` 50. Discord enforces the range on the `km` option and the server checks again. Reason for the values, observed November 2026 around Seattle (47.6062, -122.3321), qualifying events May–October 2026: 40 km has 6 events, 228 entries, 224 with a commander and 6 commanders with 10+ (not reportable), because Tacoma's venues are 40.5–43.9 km away; 50 and 60 km have 20 events, 576 entries, 481 with a commander, 13 commanders with 10+ (reportable); 80 and 100 km have 23, 661, 562, 15 and equal the five-town list (Tacoma, Issaquah, Lacey, Burien, Bremerton); 150 km 26, 729, 621, 17; 200 km 51, 1,240, 719, 21. Washington as a whole: 34, 965, 820, 19.
  - Observed in the same data: distances from Seattle are Burien 15 km, Issaquah 22, Bremerton 24, Tacoma 40.5–43.9, Graham 61, Lacey 73, Mount Vernon 89, Victoria BC 120, Vancouver BC 188. A 100 km circle holds nothing outside Washington; 150 km adds Victoria (3 events); 200 km adds Vancouver BC (28 events outside Washington). New York at 200 km spans 5 states. Beyond 200 km a state or country place is the better tool.
  - Observed in the same data: 5,155 of 6,187 qualifying events (83%) have coordinates and every one of them is geocoded; the other 1,032 can never match a radius.
  - Matching is a bounding box, then the distance. The longitude box is skipped when it runs past ±180°, so a circle across the antimeridian is not cut. The box is honest bookkeeping more than speed. Observed November 2026 on Supabase: the bare distance test over all 20,800 tournaments takes about 9 ms of server time with no box and no index, and the box makes no measurable difference. `tournaments_lat_lng_idx` is for queries that start from a center (the fallback anchor), not for stats.
  - `haversine_km` returns null when a coordinate is null. It needs the explicit test: `least()` skips nulls, so without it a missing coordinate read as 20,015 km (half the Earth's circumference). It is not declared strict, so the planner can still inline it.
  - The center is stored on the place and never moves afterwards. The same center (to about 100 m) and distance twice in one region is a duplicate (`region_places_radius_idx`).
- **Centers a radius can use** (`region_center_options`, the `around` option). Two sources in one list: every Natural Earth populated place that geocodes to a country (id `n:<ne_id>`), and every city with a qualifying event that has coordinates, at the average of its events' coordinates (id `e:<country>:<admin-1>:<city key>`, all time, not 12 months). Where both name the same city in the same country and admin-1 (on the place's name or its ASCII name) it is one row at the Natural Earth point with both counts. Labels: "Seattle, Washington, United States (metro pop. 3,074,000)", "Issaquah, Washington, United States (11 events)", "Tacoma, Washington, United States (metro pop. 719,868, 57 events)". If `populated_places` has not been loaded, only cities with events are offered.
  - Observed November 2026 on a local copy of the Supabase data: 7,871 centers (7,327 populated places with a country, 544 cities known only from events; 275 cities are in both).
  - Observed for the same data: averaging a city's event coordinates is safe. Across 819 cities the farthest event is a median 0 km, 95th percentile 6.35 km and at most 23.5 km from its city's average point; 20 cities exceed 10 km.
  - Natural Earth is a list of centers, not of every town. Observed in the pinned file: Washington has 16 places (Seattle, Everett, Tacoma, Spokane among them) and Bellevue is not one of them. Seattle at 50 km covers Bellevue.
  - Population is Natural Earth's `pop_max` (metro area), shown only to tell same-named cities apart.
- **Bulk add and remove.** `/region add` has `place`, `place2` … `place5` (autocomplete), `list` (free text), `around` (autocomplete over centers) with `km` (integer), and `region`. `/region remove` has `place` … `place5`, `list` and `region`. Every option is optional for Discord; the command replies with a hint when none is given.
  - **Why this shape.** An autocomplete option holds one value: picking a choice replaces what was typed, and a value is at most 100 characters, so one option cannot collect several places. Admins also can't guess which cities exist (typing "Seattle" finds nothing), so discovery through autocomplete stays the main way in, five picks per command. The `list` option is for more than five, or for pasting; it has no autocomplete and is matched on the server (the deferred reply has no 3-second limit).
  - **Matching** (`src/server/place-matching.ts`, pure). Names are compared after trimming, lower-casing and removing accents and full stops; they must then be equal. There is no prefix or fuzzy matching. A qualifier may follow: a state or country by name or code ("Tacoma WA", "Tacoma, Washington", "Vancouver BC", "Tacoma, US-WA"). States and countries answer to their codes too ("WA", "US", "USA", "UK").
  - **Never guess.** A name with several candidates is reported with its options and nothing is added for it: "Vancouver" (British Columbia or Washington), "ID" (Idaho or Indonesia). Candidates are the places the autocomplete would offer, so ambiguity follows the data. Observed November 2026: "Vancouver" matches only British Columbia today, because Vancouver, Washington had no qualifying event in the last 12 months; "Springfield" matches Missouri and Virginia.
  - **List grammar.** Semicolons or line breaks separate places when the text has any, and then commas belong to the place ("Tacoma, Washington; Portland, Oregon"). Otherwise commas separate ("Tacoma, Issaquah, Lacey"). In a comma list a bare state or country code after a city is read as its qualifier ("Tacoma, WA, Portland, OR"). A full name there that is also a place by itself ("Portland, Oregon", "50 km of Seattle, Washington") could be one place or two, so it is reported as such and nothing is added; the reply says to use semicolons. A label pasted whole from the list ("Tacoma, Washington, United States") is one place. A radius can be written in the list: "50 km of Seattle", "within 80km of Tacoma WA". At most 60 items are read (`listItemsMax`).
  - Text typed into a `place` option without picking is one place, commas and all. A place already picked in another option of the same command is left out of the next option's list.
  - **Reply** (`addSummary`, `removeSummary`): one message with the sections that apply. Added; Already in the region (also a place named twice in one command); More than one match (with the options); Could be one place or several; Not found (with a pointer to `around` when the name is a known city without events); Can't be used (a radius outside the range, `km` without `around`); Not added because the region is full. Partial success is applied and stated exactly. Lists are cut at 12 entries with "+N more" and the message at 1,900 characters.
  - All of one command's places are added in one transaction under the server's advisory lock, in the order given, so the 25-place limit holds whatever arrives together. Removal matches names against the region's own places with the same rules.
- **Stats: facts from the custom region, statistical sections from a region that can carry them.** A custom region never falls back as a whole (a standard region still does, through `resolve_region`).
  - Fact sections always use the custom region's own data: scene, Winners, Top players, Rising players, Top-cut appearances, Coverage.
  - If the custom region is reportable, Most played, Best results, Top-cut conversion and Rising/Cooling commanders are its own too, and the post reads like any standard one.
  - If not, `loadPostData` sets `PostData.statsRegion` and loads Most played, Best results and Top-cut conversion from it; Rising and Cooling commanders are omitted and the trend query is skipped. `statsRegion` is the anchor, or the first reportable region above it (`customStatsRegion` in `scripts/lib/post.ts`, walking up one level at a time).
  - The anchor (`custom_region_anchor`) is the smallest selectable standard region containing every place: each place walks up `parent_region_id` (a city from its state, then country, then continent) and the deepest region common to all wins. Levels a server can't select (US census regions, Spanish provinces) are skipped. Tacoma → Washington; Tacoma + Portland → United States; Tacoma + Vancouver BC → North America; anything across continents → Global. A seeded multi-state region such as Pacific Northwest is never an anchor for a set of states, because it is not on their parent chain. Nothing is stored: the answer follows the places and the data. A radius contributes its center's state and the state of every qualifying event inside the circle (`standard_region_for`), so the anchor contains every event the post shows: Seattle at 50 km → Washington; Seattle at 200 km, which takes in Vancouver BC → North America; New York at 200 km → United States. A circle that crosses a border on the map with no event across it stays with the center's state, and moves up by itself when an event appears there. Reason: a radius has no parent chain, and anchoring on the center alone would label Germany-wide stats "Baden-Württemberg" for a circle around Ulm that includes Neu-Ulm in Bayern.
  - The composer shows the two scopes with one note in the description ("Commander stats: Washington (United States), because Seattle Metro had too few entries.") and the region's short name in the three statistical headers ("Most played — Washington (6 months)"). The note is the first line of the first embed's description, above the headline, and the headline's most played line names the region too ("… is the most played commander in Washington"). Layout, budget and trim order are those of any post. In a mixed-scope post Top-cut appearances shows counts only below `POST_CONFIG.topCutShareMinCuts` (30) top cuts in the month. A month with no events gets "No qualifying events in <region> in <month>."
  - Observed November 2026: of 488 cities with commander entries in the last 6 months, 13 are reportable alone, so most city regions fall back. "Seattle Metro" as Tacoma alone: 14 events in 6 months, 348 entries, 257 with a commander, 6 commanders with 10+ (not reportable; Washington has 19). Tacoma + Issaquah + Lacey + Burien + Bremerton: 562 entries with a commander, 15 commanders with 10+ (reportable).
- **Limits** (`REGION_CONFIG`): 5 custom regions per server, 25 places per region (a continent is one place, and so is a radius), a radius of 10 to 200 km, names up to 40 characters after cleaning with `sanitizeOrganizerText` (no links, invites, mentions or markdown; empty names rejected). Changes to one server's regions are serialized with a transaction-level advisory lock so two commands can't pass a limit together.
- **Lifecycle.** Deleting the server's current region sets the server back to Global in the same transaction and says so. `/region set` refuses a region with no places. The cron's prune step deletes a departed server's config and its custom regions, including servers that own regions but never set a channel (`deleteGuildData`).
- **Attribution.** Replies from the region commands name places only and carry no TopDeck attribution. Autocomplete choices show event counts, which are TopDeck-derived, and Discord gives choices no room for attribution. The `around` choices also show event counts, and Natural Earth's metro population (public domain, no attribution required).
- **Performance.** `region_tournament_ids` stays one query: the owned-region test is OR-ed in behind a one-time check. Observed November 2026 on a local copy of the Supabase data: writing it as a second `UNION ALL` branch gave identical results but stopped the planner from driving from the region's tournaments, and every standard-region stat took 0.2–0.4 s longer. Observed on Supabase with SELECTs emulating the new filter (times include about 0.1 s round trip): standard regions are unchanged (global 6-month commander grouping 0.68 s before, 0.67 s after; Washington 0.23 s and 0.25 s; same rows); Tacoma alone 0.23 s; the 25 biggest cities as one region 0.41 s; three continents as places 0.67 s. A fallback post for Tacoma loads in about 2.9 s, against about 10 s for today's standard Washington post. The fallback walks up lazily because `resolve_region` scores every level to global (1.5 s for Washington, where one check is 0.23 s). Autocomplete lists: standard regions 0.11 s, cities 0.13 s, countries without a region 0.11 s, then cached. Migration 016 rewrites the owned-region branch as two tests: one lookup in `region_members` for all of the region's member regions at once (their ids collected into an array), and one pass over the region's other places with a `case` that sends a radius row to the distance test and never to the country test (a radius row carries its center's country, so it would otherwise match the whole country). Observed November 2026 on a local copy of the Supabase data: all 108 standard-region stat checks hash identically before and after, existing custom regions return the same tournaments, and the two-test form is faster than migration 015's three separate tests (a single city 0.64 s to 0.35 s; three states and a city 3.0 s to 0.58 s; Seattle at 50 km 0.31 s; local timings, slower than Supabase). A single `exists` with one `case` over all places was slower for member regions. The anchor of a radius region takes 63 ms locally. Observed on Supabase with SELECTs emulating the radius filter (times include about 0.1 s round trip): 6-month commander grouping for Seattle at 50 km 0.14 s, New York at 200 km 0.44 s (2,515 entries), Washington through the existing function 0.15 s. Centers list: `region_center_options` takes 0.21 s locally for 7,871 rows (0.71 s before the country names were joined once instead of looked up per row), and a cold instance builds the cached list in 0.6–0.8 s locally including the JavaScript side; matching a typed prefix against it takes about 2 ms. On Supabase the event side of that query takes 0.13 s warm (0.84 s on the first run); the populated-places side can't be measured there until the table is loaded.

## Stack

- TypeScript, Node 22.21+, scripts run with tsx
- Postgres on Supabase, accessed with postgres.js. No ORM, no Prisma, no supabase-js.
- Migrations are numbered plain SQL files in db/migrations, applied by a small script
- Next.js 16 (app router, pinned 16.4.3) on Vercel: `app/api/interactions` (signed Discord interactions), `app/api/cron` (daily, `vercel.json`), and an install/privacy page. Server code is in `src/server/`. No discord.js: plain REST over fetch; Ed25519 via Node crypto.

- On Vercel, `DATABASE_URL` is the Supabase transaction pooler (port 6543); `connect()` already sets `prepare: false`.

- Cloud sessions: Node's built-in `fetch` ignores `HTTPS_PROXY` unless `NODE_USE_ENV_PROXY=1` is set (needs Node >= 22.21). Set it in the cloud environment's variables. Node then prints an experimental-feature warning (`EnvHttpProxyAgent`) to stderr, which is harmless.

## Hard rules

- Data comes only from the documented TopDeck API. The bot also calls the Discord API to answer commands and deliver posts, and uses Supabase as its database. The bot and scripts never access cedhstats.org, topdeck.gg HTML pages, or any other data source. Four exceptions:
  - Claude Code may read https://cedhstats.org/about as documentation for stat definitions. Code never fetches cedhstats.org. Use methodology as defined at https://cedhstats.org/about.
  - The Natural Earth boundary file is downloaded once, by hand, into gitignored `data/`, pinned to tag v5.1.2 and verified by SHA-256 in `scripts/geocode.ts`: `curl -o data/ne_10m_admin_1_states_provinces.geojson https://raw.githubusercontent.com/nvkelso/natural-earth-vector/v5.1.2/geojson/ne_10m_admin_1_states_provinces.geojson`. Scripts never download it.
  - Natural Earth populated places, for radius centers only. `ne_10m_populated_places_simple.geojson` is downloaded once, by hand, into gitignored `data/`, pinned to the same tag v5.1.2 (released 2022-05-13, public domain; 4,932,147 bytes, 7,342 places) and verified by SHA-256 (`fd3fa867a320cbd5c5b6bb5bc550afeec2939fb2cef688e508007282a55ac42f`) in `scripts/load-populated-places.ts`: `curl -o data/ne_10m_populated_places_simple.geojson https://raw.githubusercontent.com/nvkelso/natural-earth-vector/v5.1.2/geojson/ne_10m_populated_places_simple.geojson`. Only that script reads the file, and it never downloads it. Stored per place: Natural Earth id, name, ASCII name, coordinates and `pop_max`, plus the country and admin-1 our own geocoding gives the point; the file's other properties are dropped. The bot and the Vercel app never fetch or read the file at runtime; they read `populated_places`.
  - Scryfall, for partner validation and commander color identity only. `scripts/fetch-pair-commanders.ts` may call Scryfall's card search API (`https://api.scryfall.com/cards/search`) with the query `oracletag:pair-commander` and store the card names in `pair_commanders`. `scripts/pair-report.ts` may run the same query plus `type:background` and `type:"time lord" type:doctor`, in memory and read-only, to check the tag still covers both sides of every pairing. `scripts/fetch-color-identity.ts` may call the same search API with the query `is:commander or oracletag:pair-commander` and store each card's names and color identity in `commander_colors`, for the color squares in the post; `scripts/color-report.ts` may run that query in memory and read-only, to report how many registered commanders match. No other query, endpoint or script. Only names and color identity are stored. No images: no image or image URL is read, stored, linked or shown anywhere. Type line, keywords and rules text are read in memory by the pair report and never stored. Requests are sequential, 1 per second, send `Accept: application/json` and the User-Agent `FieldReport/1.0 (https://github.com/EshaanS/cedh-meta-bot)`, honor 429 and Retry-After, and never carry the TopDeck key. The bot and the Vercel app never call Scryfall at runtime; they read `pair_commanders` and `commander_colors`.
- Player data (permitted by TopDeck, `docs/permissions.md`, on condition that we keep attribution, keep names current and honor privacy requests):
  - Store the TopDeck player id and display name only. Never request or store decklists or Discord fields.
  - Store account ids only (28 characters; `playerId` in `scripts/lib/topdeck.ts`, enforced by check constraints). Players without an account get a new id per event, so they are stored with a null `player_id`, are never named, and count for no player stat.
  - Refresh names on every ingest.
  - Treat "Deleted User" or a missing name as removed: store a null name and never show the player.
  - Honor the opt-out list (`player_optouts`) in every output: posts, `/preview`, `report`, logs and fixtures. Read names only through the `player_names` view.
  - Scripts and logs print player ids or counts, never names, except the outputs that exist to show them (posts, `/preview`, `preview`, `report`). Committed fixtures use invented names.
- Always pass `columns` explicitly. Whitelist fields before any DB write and drop everything else. Exception: the single-tournament standings endpoint (GET /v2/tournaments/{TID}/standings) ignores `columns` and always returns every player's name, ID and decklist. Only the standing-1 row's `standing`, `leader`, `id` and `name` are read (`pickStandingOne`); every other row and field, including decklists, is discarded in memory and never printed, logged or stored.
- Every message that displays TopDeck-derived data (monthly posts, `/preview`) shows "Data provided by TopDeck.gg" with a link to https://topdeck.gg. Pure configuration replies that show no TopDeck data (`/region set`, `/channel set`, `/region show` without stats) don't carry it.
- The API key comes from env only and is never logged or printed.
- Make requests sequentially. Honor 429 responses and the Retry-After header. The default limit is 100 req/min, but the bulk endpoint has a lower, unpublished limit, so pace bulk calls conservatively.
- Every script must be idempotent and resumable: use upserts, and skip work that is already done.
- Explain why before adding any dependency.
- Do not expand scope beyond the task given.
- Supabase Data API is disabled; access is only via postgres.js as the table owner. Automatic RLS is on with no policies. If queries ever return unexpectedly empty, check which role is connected.

## TopDeck API facts (from docs unless labeled "Observed"; verify against real responses)

- Base URL: https://topdeck.gg/api. Header: `Authorization: <key>` with no "Bearer" prefix.
- Bulk search: POST /v2/tournaments with `{ game: "Magic: The Gathering", format: "EDH", start, end, columns }`. Dates are unix seconds. Returns completed events only. League events are excluded unless `leagues: true`.
  - Observed in November 2026 testing: a bulk call made a few seconds after the previous one returned 429 with `Retry-After: 8`. Seen once so far. Keep pacing bulk calls (backfill waits 10 s between them) and always honor Retry-After.
- Bulk `eventData` is documented as lat, lng, city, state, address, headerImage. It has no country field. `address` is organizer free text and can be "Online".
  - Observed in October 2026 data: bulk `eventData` does include `country`, present on ~56% of events (912 of 1632) and non-blank on ~55%. This contradicts the docs.
  - Observed in the 12-month Supabase backfill (November 2026, reported by the user; the local Sep–Oct 2026 test data cannot confirm it): bulk `eventData.country` is absent on all events before February 2026 and appears from February–March 2026 onward. So country coverage figures above describe post-February events only.
  - Observed in the 12-month Supabase backfill (November 2026, reported by the user): every event with a country also has lat/lng (100%, every month), and no event has a state or country string without lat/lng. About 26.5% of 16+ events have no location at all. This supersedes an earlier note that older events "have state and often lat/lng": lat/lng is the most complete location field.
  - Observed in October 2026 data: there is no "Online" address convention. No address was "Online", and only 3 matched online-sounding terms, 2 of them Discord invite links. ~40% of events have no location field at all (no non-blank lat, lng, city, state, address, or country). Whether those are online events is unverified.
- Bulk standings rows return `name` and `id` when those are in `columns`.
  - Observed in the 36-month Supabase backfill (November 2026, December 2023 – October 2026): `id` is a string of 28 characters (49,495 ids, 6.1 events each on average, up to 250) or 20 characters (82,394 ids). Every 20-character id appears in exactly one event, so those are per-event ids for players without an account, not player identities. Every entry carries some id from May 2024 on (about 70% before that; 99.2% of qualifying entries overall), but only account ids are kept: 73% of October 2026 entries (19,061 of 26,126), and 7,892 of the 9,720 bracket winners that had an id. 82 account ids had no usable name (missing or "Deleted User").
  - Observed in the same data: 19 (event, account id) pairs appear on two standings rows (2 of them in qualifying events, neither with both rows in the top cut). Player stats count each (event, player) pair once (`qualifying_player_events`, migration 011).
  - Observed for October 2026: account ids are far more common in qualifying events than overall. 96% of global qualifying entries have one (99% Pacific Northwest, 100% Europe) against 73% of all entries, so players without an account are mostly in small or casual events.
- Standings rows include `leader` (the commander name; partners appear as "A / B", alphabetical) when a deck was submitted. Otherwise it is absent. Expect roughly 40% of entries to have no commander.
  - Observed in October 2026 data: `leader` is present on ~34% of standings rows overall, so ~66% have no commander. Coverage rises with event size: ~12% of rows in events under 16 players, ~30% at 16–31, ~69% at 32–63, ~88% at 64+.
  - Observed in the 12-month Supabase backfill (November 2026, reported by the user): per-event leader coverage of unlabeled events is bimodal, 38% at 0% and 38% at 75% or more. This is why unlabeled events are classified by their series' average coverage.
  - Observed in October 2026 data: standings rows carry a `players` key only in team events (`isTeamEvent: true`; 1 event and 6 rows that month). Ingestion drops team events.
- The bulk response has no rank/standing column. Preserve the array index, but do not treat it as rank until verified.
  - Observed in November 2026 (user's check of Breach the Bay 2 on TopDeck): topCut = 0 means no bracket was recorded, not that there was no cut. That event had a top 16 that isn't recorded as bracket rounds, used Japanese point-pool scoring instead of 5/1/0, and TopDeck names its winner. Swiss points therefore cannot rank these events.
- GET /v2/tournaments/{TID}/standings (observed November 2026) returns one row per player with name, id, leader, decklist, deckObj, standing, points, winRate, opponentWinRate. It ignores `columns`. Standing 1's `leader` for Breach the Bay 2 matched the winner TopDeck shows. Of 38 local qualifying 32+ events with topCut = 0, 28 had a standing-1 commander and 10 had a standing 1 without one.
- GET /v2/tournaments/{TID}/info returns `location` with name, city, state, country, lat, lng. Every subfield is nullable, and the whole object can be null.
  - Observed in October 2026 data: `location` was never null in 30 sampled calls. Events with no location returned an object with every field null. Keep handling null anyway.
  - Observed in September–October 2026 data: for tournaments with no bulk country, `/info` returned a non-null country 0 of 50 times (95% upper bound 7.1%). Decision: we are not building country enrichment from `/info`.
- State values are inconsistent ("WA" vs "Washington" vs "Lombardia"). Never key regions on raw strings.
## Geocoding facts (Natural Earth 1:10m admin-1, v5.1.2)

- Observed in November 2026: admin-1 granularity differs by country. US and Canada are states and provinces; Germany has 16 states; Spain has 52 provinces; Italy has 110 provinces; France has 101 departments; the UK has 232 counties and unitary authorities. Check a country's level before defining admin-1 regions there.
- `geo_admin1_group_code` / `geo_admin1_group_name` hold one grouping level per country, chosen in `scripts/geocode.ts`: Natural Earth `region` where at least 90% of the country's features have a `region_cod` (Spain's autonomous communities, Italy's regions, France's regions); else `geonunit` where the country has 2+ (UK nations, Belgian regions); else `region` where at least 90% have one (US census regions, e.g. US-WEST); else none (Germany). Group codes are `<ISO2>-<SLUG of the group name>`, e.g. ES-CATALUNA, GB-SCOTLAND, because Natural Earth's `region_cod` values are inconsistent (13 formats, duplicates such as Ceuta and Melilla both `ES.CE`).
- `iso_a2` is a real code for every country we have seen; only 12 disputed or special features use -1/-99 (e.g. Northern Cyprus, Somaliland), and those geocode with a null country code.
- Observed in November 2026 testing: 1:10m borders are coarse at border cities. One Detroit riverfront venue geocoded to Ontario; that was the only country mismatch against the bulk country string in 3,763 events.

## Stat definitions

- Stat definitions follow https://cedhstats.org/about. Any deviation must be listed below with its reason.
- Comparison source: the user's reading of cedhstats.org/about, given to Claude Code on 2026-11-07 (Claude Code could not fetch the page from the cloud session).

### Same as cedhstats
- Points per game: PPG = (5W + 1D) / (W + L + D).
- Neutral baseline: 1.25 - 0.25 x draw rate (a random seat in a 4-player pod).
- Shrinkage: adj = (n x PPG + 20 x 1.25) / (n + 20). The target is the fixed 1.25, confirmed from cedhstats' Sleeper Pick and Meta Trap definitions. Note: 1.25 is not the draw-adjusted baseline, so in high-draw fields shrunk scores sit slightly above neutral.
  - n = entries (inferred, not stated): cedhstats does not define n, but every other sample size on its page is counted in entries (75+ entries, 16 decklists, 0.2% meta share).
- Deck stats only for commanders with at least 0.2% meta share.
- Entries with an unknown commander (no `leader`) are excluded from commander stats.

### Deviations, each with its reason
1. Event filter. cedhstats includes all 16+ events; we also exclude `event_class` casual, unlabeled_casual and test. Reason: casual and bracket nights are ~14% of 16+ events (user's 12-month run) and would otherwise appear in winners and highlights. Counting unlabeled_casual and test too, the filter removed 38.8% of 16+ events in local May–October 2026 data, but only 5.2% of their entries with a leader (2,256 of 43,565; 31.3% of all entries), because the removed events rarely record commanders.
2. Region. cedhstats uses normalized location strings; we reverse-geocode lat/lng with Natural Earth admin-1. Reason: every located event has coordinates, while the strings are inconsistent (Cataluña/Catalunya/Catalonia, CA/California).
3. Top-cut membership. cedhstats uses standing <= top_cut; we use bracket games played (wins_bracket + losses_bracket > 0). Reason: the bulk endpoint has no standing field, and array order is not verified as rank. Known gap: a player whose top-cut pod drew counts as not top cut. Events with topCut = 0 can still have had an unrecorded cut; their entries count toward no top-cut stats (conversion, top-cut appearances).
4. Partner validation. cedhstats excludes invalid partner pairs using Scryfall `oracletag:pair-commander`. Implemented the same way (migrations 012 and 013): `qualifying_entries.leader` is null for a pair with a half missing from the list, so those entries count for no commander stat (meta share and its denominator, PPG, conversion and its baseline, top-cut appearances, trends, reportability). They still count as entries, as players' registered decks, and in Winners. Remaining differences from cedhstats: our rule is membership only (both halves in the list; it does not check that the two cards' abilities go together), and when `pair_commanders` is empty nothing is excluded.
   - Observed November 2026 (`pair-report`, Supabase, December 2023 – October 2026): 435 distinct pair leaders in 38,891 entries. Invalid: 148 leaders, 161 entries in all data; in qualifying entries of May–October 2026, 53 leaders with 53 entries, which is 0.37% of pair entries and 0.13% of the 41,179 entries with a leader. Every invalid pair in that window appears once, so no commander ranking can change.
   - Observed in the same run: the tag has 232 cards (827 printings) and includes both sides of every pairing: all 30 Backgrounds and all 17 Doctors, so no extra Scryfall query is needed. Among pairs with both halves in the list, none combine abilities that don't go together (0 of 287), so membership and a full legality check agree on today's data.
   - Name matching, observed in the same run: 99.30% of pair-half entries match Scryfall's Oracle names exactly. Two systematic mismatches account for the rest of the valid ones: a curly apostrophe in older events ("Kraum, Ludevic’s Opus", 211 entries, and "Wernog, Rider’s Chaplain", 5), fixed by `card_name_key`; and Universes Beyond printed names (the Stranger Things cards: "Will the Wise" for Wernog, Rider's Chaplain and four others, 24 entries), fixed by storing printed and flavor names. Letter case, accents and other punctuation changed nothing. Pairs are always written in alphabetical order, never in both orders. The 227 halves still unmatched are real cards that cannot pair (e.g. Kinnan, Bonder Prodigy).
   - Effect of the exclusion, observed November 2026 on a local copy of the Supabase data that reproduces its stats exactly (October 2026 report, May–October window). Global: 53 one-entry commanders leave the list, entries with a commander go from 41,179 to 41,126, meta shares rise in the fourth decimal, the conversion baseline moves from 25.891% to 25.887%, and no commander changes rank in meta share, PPG, conversion, top-cut appearances or the share trend. In `stat_growth` (used only by `report`) seven commanders around ranks 98–104 swap places because the denominators moved. Pacific Northwest: nothing changes at all. The composed posts for both regions are identical, character for character.
   - Apostrophe normalization (ours, not from cedhstats). Observed November 2026 across all data: 26 leader spellings use the typographic apostrophe U+2019 (21 single commanders with 135 entries, 5 pairs with 217), all from June–August 2025 (349 of the 352 entries in June 2025). Normalizing takes the 1,875 distinct leaders to 1,851: 24 spellings merge into an existing commander (350 entries, e.g. 209 into Kraum, Ludevic's Opus / Tymna the Weaver, 31 into Glarb, Calamity's Augur, 30 into Yuriko, the Tiger's Shadow) and 2 are only respelled. None are in the last 6 months, so current posts don't change; a report whose window includes June 2025 does (global June–August 2025: Kraum / Tymna goes from 1,053 to 1,242 entries, and Glarb and Yuriko each move up four places).
   - Known gap, not addressed: a pair written with a printed name is a different commander string from the same pair written with Oracle names ("Tymna the Weaver / Will the Wise" vs "Tymna the Weaver / Wernog, Rider's Chaplain"). Both are valid; they are just counted separately. About 24 entries across all data, at most 4 in the last 6 months.
5. Not implemented: player rating, entry points, Deck of the Month, Rising Star, Floor/Veterans/Ceiling, and all pod and seat stats. Reason: they need round data, which we don't ingest, or rating models we haven't built. Our Top players and Rising players sections are our own definitions (Player stats below), not cedhstats'.
6. Recency. cedhstats refreshes the previous month during the first week of the new month; we re-fetch every month that ended less than 14 days ago on each run.
7. Deck-stat minimum. cedhstats shows deck stats for commanders at 0.2%+ meta share; we also require at least 10 qualifying entries with a leader in the window, for PPG and top-cut conversion (`stat_eligible_commanders`). Reason: the 0.2% floor is calibrated at global scale (0.2% is about 86 entries locally); in a region it admits 2-entry commanders (Washington: 70 of 89 PPG rows were under 10 entries). 10 matches the reportability threshold, so the stats and the reportable test cover the same commanders.
8. Event winner. cedhstats takes the winner from standings (rank 1); we derive it from bracket records in the `tournament_results` view, because the bulk endpoint has no standing field. Winner = the single top-cut entry with the most bracket wins and zero bracket losses. If none: 'final drawn' when 2+ top-cut entries share the most bracket wins with zero losses, else 'no single winner'; events with topCut = 0 (no bracket recorded) use the official standing-1 commander from TopDeck's standings endpoint (`event_winners`), shown as 'winner', or 'winner not recorded' when it has none. Observed in local May–October 2026 data (qualifying events with topCut > 0): the rule finds a winner in 1,248 of 1,396 events (89.4%), and every one of them is standings array index 0; 146 are 'no single winner' and 2 'final drawn'. Index 0 alone is not a safe winner: it has strictly the most bracket wins in only 67.8% of these events. A top-4 pod that drew records no bracket games, so it shows as 'no single winner', not 'final drawn'. The winning player comes from the same row (`tournament_results.winner_player_id`), or from the standing-1 row for topCut = 0 events (`event_winners.winner_player_id`).

### Player stats (our own definitions, not from cedhstats)
- Events: the region's qualifying events (16+, cedh or unlabeled_competitive) in the end month. Winners stays 32+.
- Event win: an event whose result is 'winner' (`event_winner_players`). A standing-1 player with no recorded commander is 'winner not recorded' and counts as no win.
- Top cut: bracket games played, as in deviation 3, so topCut = 0 events give no top cuts. Wins, top cuts and recorded events are counted per distinct (event, player) pair, never per standings row.
- Top players (`stat_top_players`): up to 5 players with at least one win or top cut, ordered by wins, then top cuts, then the largest event they won or cut; shown with their most-played commander that month.
- Rising players (`stat_rising_players`): up to 3 players, at most one per event, largest event first, whose win or top cut in the region that month is their first event win in our data, their first top cut in our data, or a top cut within their first 5 recorded events. History is the player's qualifying events worldwide, not only in the region, and goes back only as far as the backfill (36 months), so "first" means first in that window. One per event: each player's best qualifying event is chosen first, players with no visible name are dropped (so an opted-out player never uses up an event's line), and within an event the pick is by reason (first win, first top cut, top cut in first 5 events), then most bracket wins, then name. With fewer than 3 such events the section has fewer lines.
- Entries with no account id (players without a TopDeck account) count for no player, and a winner without one shows the commander alone. Players with a null name (removed or opted out) are left out of both lists.
